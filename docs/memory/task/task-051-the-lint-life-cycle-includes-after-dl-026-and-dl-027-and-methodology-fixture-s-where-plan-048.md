## Context

dl-026 and dl-027 (approved 2026-10-26, plan-047) amend `software`'s `delivery` contract and
spec-001 §9 and §18:
- a methodology's `delivery` includes `release` and `retrospective` directly or through
  sub-workflows the same methodology ships, at any depth, each shipped in the same part as
  `delivery` (`contents` or the conditional part, spec-001 §6.5); a sub may be included by several
  phases, and `release` need not be reached on every path (dl-026 D1);
- every phase that includes `release` iterates over `release` with a `where` whose `status` is
  `[in-development, releasing]`; any other key of that `where` is a frontmatter field the composed
  `release` type declares, the methodology's own tightening included; key values are not checked
  (dl-027 D1, D3).

`life-cycle-includes` (`src/workflow-rules.ts`, `lifeCycleProblems`) checks today only that
`workflows/delivery.yaml` itself includes `release` and `retrospective` by name; it reads no `where`.
The composer applies the same rules, so it refuses `scrum`'s accepted shape, whose `sprint` sub
includes both. dl-026 D3 and dl-027 D3 name this task; dl-027 D5 moves `methodology/fixture`'s
`where` here, agreed with plan-046's session, which owned the fixture.

## Acceptance

`npm run build` precedes the commands.

1. **Reach.** For a methodology's `delivery`, the rule follows `include` names only into
   workflows the pack itself ships, with a visited set (an include cycle neither loops nor
   errors); it reports `life-cycle-includes` when `release` or `retrospective` is reached from
   `delivery` by no path; it reports nothing when either is reached through one of the pack's
   subs, at any depth, or by several phases.
2. **Part.** A workflow reached from `delivery` that the pack ships in another part than
   `delivery` (`contents` against the conditional part) is reported (spec-001 §18, dl-026 D1).
3. **`where`.** Every phase, in `delivery` or in a reached workflow, whose `include` is `release`
   is reported unless it has `iterate_over: release` and a `where` whose `status` is exactly
   `[in-development, releasing]` (any order); a further key that is no frontmatter field of the
   composed `release` type (the required fields and template fields of the packs the methodology
   requires, and its own `memory.yaml` tightening) is reported; a key's value is not checked.
4. **Messages** name the rule as amended (spec-001 §9, dl-026, dl-027) and the phase or the
   workflow they concern; `software`'s `sw-life-cycle` check is unchanged.
5. **Fixtures.** Every fixture methodology whose `delivery` includes `release` follows the rule:
   `tests/fixtures/software-exit/packs/methodology/fixture/workflows/delivery.yaml` moves to
   `status: [in-development, releasing]` (dl-027 D5), and the golden trees and merge examples
   (`tests/fixtures/compose/tree/`, `tests/fixtures/merge/`, the test constants of
   `tests/check-packs.test.ts`), whose `software` declares no `release` type, are brought to it as
   the Design decides, their expected outputs regenerated by the repository's commands, never by
   hand. A Design that finds a fixture cannot follow the rule goes to the approver (dl-019).
6. **Validation.** `npm run validate` passes; `npm run validate -- --overlay
   tests/fixtures/software-exit` passes with 7 matrix runs and 0 failed; the fixture README's
   generated sections stay in step (`tests/readme-generate.test.ts`).
7. **Red first** (dl-018): the tests of 1–3 are written before the change and fail on `main`'s
   lint, each red run recorded in the Execution Notes (command and failing count); the counts the
   change moves are stated.
8. **Tests:** `npm test` passes on Node.js 22.21 and on the floor 22.12.0, in clean clones; the CI
   run on the branch is `success` and recorded. No file under `packs/` or `.wingfoil/` changes; no
   new dependency.
